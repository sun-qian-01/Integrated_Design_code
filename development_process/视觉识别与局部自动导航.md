# 从手机画面识别通路并进行局部自动导航

## 当前实现与适用范围

新增 `vision_navigation.py`，复用 `phone_direction_control.py` 和已保存的 `phone_direction_points.json`。八方向坐标没有被覆盖。

当前按你选择的“单色地面、与地面明显不同颜色的障碍物”实现。程序连续读取手机截图，分割与标定地面颜色相近、且与画面近处连通的区域，比较左、中、右通路；只有在启用实车模式并在窗口启动后，才发送短时动作。

你已反馈：左上/右上是向左前/右前行驶，左下/右下是倒车转向；单独左/右只转车轮。因此首版预填的映射是：

| 决策 | 屏幕按钮 | 行为 |
| --- | --- | --- |
| `forward` | `up` | 预期前进，启用前再核对 |
| `turn_left` | `up_left` | 向左前方行驶，不是原地左转 |
| `turn_right` | `up_right` | 向右前方行驶，不是原地右转 |
| `stop` | 不发送下一次动作 | 当前定时触摸完成后释放；依赖 App 松开即停车 |

本版不使用倒车和单独左/右，也不假定车轮在松开后会自动回正。转弯后的实际轨迹需要重新观察。

**这是受控场地的局部避障原型，不是已验证的自主驾驶或全局寻路系统。** 当前没有目标点、定位、地图、A* 或到达判定。颜色相似不代表物理可通行，红色区域也仅代表“非地面色/未连通/不确定”，不是可靠物体识别结果。

## 一、现在即可做的操作

已在项目的 `.venv` 中安装 OpenCV 和 NumPy，不需要修改系统 Python。

首先让手机停留在横屏的小车控制 App。以下命令在项目目录的 PowerShell 中执行。

### 1. 只读检查画面

```powershell
.\.venv\Scripts\python.exe .\vision_navigation.py --check
```

会打印手机分辨率及一次截图的耗时，不发送触摸。若提示竖屏，请切回横屏控制页面。

本次真实设备检查能连接手机，但手机当时为竖屏，因此程序按设计拒绝继续。尚未取得可用于场地标定的横屏画面，也未触发小车运动。

### 2. 标定地面、观察区域和 App 图标

把小车放在准备好的地面，摄像头朝向行驶区域，确保近处地面可见。运行：

```powershell
.\.venv\Scripts\python.exe .\vision_navigation.py --calibrate
```

按窗口顺序操作，拖出矩形后按 Enter 确认：

1. **道路观察区**：选前方地面，尽量横跨左、中、右可行驶范围，底部应对应离车最近的可见地面。不要选整个手机画面或摄像头看不到的区域。
2. **遮罩区**：在刚才道路区内，逐个框出速度条、方向盘、文字等 App 叠加元素。每框一个按 Enter，完成后按 Esc；没有叠加元素直接按 Esc。这些像素不参与判断。
3. **地面样本**：在道路区框出一块干净、无按钮、无障碍、无明显阴影的地面。
4. **App 固定图标**：选一个稳定、实心的 App 图标区域，避免透明区域和实时视频背景，用来粗略检查是否离开原页面。

生成 `vision_profile.json`。标定会覆盖此文件，并重新关闭实车验证标志；不会改动八方向坐标文件。不要把样本选成障碍物，也不要在生成文件后手动移动道路选区而不重新标定。

道路选区会按画面宽度分为左、中、右三个区域。如果大幅裁偏，所谓“中间”不再代表小车前方；请保持摄像头固定、选区相对小车前方居中。

### 3. 运行观察模式

```powershell
.\.venv\Scripts\python.exe .\vision_navigation.py
```

- 绿色：与采样地面颜色相近，并与近处地面连通。
- 红色：疑似障碍或不确定区域，包括阴影、不同色地面等。
- 未染色：人工屏蔽的 App 元素。
- `L/C/R floor`：三个区域内的地面比例，不是距离、碰撞概率或模型置信度。
- `forward` / `turn_left` / `turn_right`：建议动作。
- `wait`：判断尚未连续稳定，或等待动作后的新画面。
- `stop`：当前不应继续动作。

不加 `--drive` 时，即使按 G 也不会驱动车辆。观察模式可一直用于调整场地、移动障碍物及检验判断。按 Q 或 Esc 退出。

## 二、识别与决策逻辑

```text
读取新的横屏截图
  → 道路区域裁剪、屏蔽手机 App 元素
  → 比较 Lab 颜色与标定地面样本的差异
  → 去除零散噪声，只保留与近处中央地面连通的区域
  → 计算左/中/右整体及近处地面比例
  → 检查截图时效、尺寸、固定图标及画面是否疑似冻结
  → 连续三帧建议一致
  → 观察模式仅显示；实车模式执行一次短按
  → 松开、等待、丢弃动作前旧画面、重新观察
```

判断规则：

1. 近处中央不够清楚时停止，不尝试盲目绕过近障碍。
2. 中间通路清楚时优先前进。
3. 中间远处受阻、近处中央和某侧均清楚时，提出向该侧前转弯的建议。
4. 左右同样可行、没有清楚通路或出现异常时停止，等待人工处理。

因此程序不会为寻找出路而随机转向，也不会在死路中自动倒车。本版转弯仍有前进分量，像素上的空地不能保证车身完整转弯轨迹可通行；需要低速、留足场地间距并实测。

实时变化用于重新评估通路和监测画面，不把“运动像素”直接认作障碍物：摄像头随车移动时，整幅背景都会运动。

## 三、完成验证后启用有限步数实车模式

目前你确认了方向按钮初步有效，但尚未确认松开后是否立即停车。本版不会在开发和测试过程中自动驱动车辆。

先用现有八方向程序确认：上键是否前进；左上/右上轨迹是否正确；50～100 毫秒短按是否有效；松开是否停止；转向是否回正或保持角度。若松开后继续行驶，本版不能直接启用，必须先接入明确的停车操作或设备控制协议。

确认通过后，在生成的 `vision_profile.json` 中设置：

```json
"controls_verified": true,
"release_stops_verified": true,
"actions": {
  "forward": "up",
  "turn_left": "up_left",
  "turn_right": "up_right"
}
```

以上是需要修改的字段片段，不是完整配置文件。保留其他标定结果。

随后启动：

```powershell
.\.venv\Scripts\python.exe .\vision_navigation.py --drive
```

- 默认仍为暂停，看到稳定通路判断后，在该窗口按 **G** 才开始。
- **空格**暂停后续动作；**Q/Esc**退出。正在执行的短按仍完成并释放，不是即时物理急停。
- 默认每次按压 **100 ms**，随后至少等待 **0.5 秒**，再获取动作完成后的新画面并累计三次一致判断。
- 每次启动最多 **20 步**，连续转向最多 **3 次**，达到上限暂停。不会无限转圈。
- 遇障或异常会退出运行状态，不会因为画面后来变好就自行恢复；重新检查后再按 G。
- 运行时不要同时用八方向面板或 scrcpy 鼠标操作，以免触控互相干扰。

日志默认追加到 `navigation_logs/decisions.jsonl`，包含建议、门控结果、区域比例、截图耗时与 `submitted`。`submitted: true` 表示提交了触控任务，不代表动作成功，更不代表小车完成了运动。

## 四、调参顺序

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| `color_tolerance` | 28 | Lab 色差容差；小了易把阴影当障碍，大了易把障碍当地面 |
| `clear_ratio` | 0.88 | 通路整体地面比例阈值 |
| `near_clear_ratio` | 0.95 | 近处地面比例阈值，比整体要求更严格 |
| `max_frame_age_s` | 1.5 | 从请求截图开始计算的最大允许画面年龄 |
| `freeze_s` | 3.0 | 道路区几乎不变时，提示可能冻结并暂停 |
| `pulse_ms` | 100 | 单次触摸时长，允许 50～200 ms |
| `settle_s` | 0.5 | 动作完成后的最小等待时间 |
| `anchor_error_limit` | 16 | 固定图标灰度平均差异上限 |

每次修改配置后重启程序。优先改善光照、固定摄像头、重新标定和屏蔽界面，不要只靠提高容差让画面“变绿”。在观察模式下分别摆放左、中、右障碍，检查每次判断是否符合实际。

静止场景也可能被判断为疑似冻结，这是有意采取的保守处理。不要仅为让车辆运行而放宽所有异常阈值。固定图标检查只是简易界面检查，无法保证任意弹窗、视频故障都能被发现。

## 五、当前限制与下一步

赛道场地已更新为 `赛道分析与自动寻路规划.md` 中的道路布景。该赛道包含深色道路、白色虚线、红白边界、黄色减速带、黑白格线和静态装饰岛，后续应优先开发道路跟踪模块；本文件中的颜色分割避障模块保留为局部障碍实验，不直接视为完整赛道寻路。

- 使用 ADB 连续截图轮询，不是直接解码小车视频流，也不承诺 30 FPS。实际采样速度由 `--check` 与界面耗时决定，适合低速停走实验。控制闭环稳定后应优先对接原始视频流。
- USB 新截图不意味着小车到手机的视频一定新鲜；App 可能显示缓存帧。画面变化检测不能代替视频源时间戳。
- 单目颜色分割没有真实距离，不识别同色障碍、透明物体、桌沿、台阶等，也未建模车宽和制动距离。首轮请用有边界的平整地面，不在桌沿附近实验。
- 少量颜色不同的细小障碍可能被比例统计或去噪忽略；标定和阈值测试必须覆盖实际障碍尺寸。
- 不提供自动倒车、搜索记忆、目标到达或迷宫解法。全部方向不明确时停下是预期行为。

下一阶段可按以下顺序扩展：

1. 在受控场地收集不同障碍位置、阴影和失败画面，标注真实可通行区域，量化漏检与误检。
2. 取得更低延迟的视频流，加入画面时间戳和明确的停止控制；测量短按对应的位移与转弯轨迹。
3. 利用地面标记、AprilTag 等建立位置和方向参考，设置终点。
4. 将场地转成栅格或路口图，再加入 A*、障碍更新、重规划与到达判定。

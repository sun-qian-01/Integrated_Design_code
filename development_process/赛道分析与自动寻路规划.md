# 预想赛道分析与自动寻路规划

## 1. 对赛道的判断

根据 `IMG_20260925_001113.jpg`，这是一张带有道路边界和车道标线的玩具赛道布景，主要视觉元素包括：

- 深色道路区域，与周围绿色背景、黄色区域和装饰物有明显颜色差异。
- 白色虚线车道线，可用于估计道路方向、车道中心和弯道趋势。
- 红白路缘线，可用于识别道路边界，但不建议把红色本身当作唯一的可行驶边界。
- 黄色减速带、黑白起止线、灰色箭头、停车区域等特殊标记。
- 岛状区域、植物、轮胎、石块和水面等静态装饰物，它们会被摄像头看到，但不应全部当作临时障碍物。
- 大量弯道、窄路和视觉遮挡，车载摄像头只能看到局部道路，无法仅凭单帧图像知道整张赛道的拓扑结构。

这类赛道与前一版“单色地面上放置明显障碍物”的测试场地不同。赛道本身已经提供了道路结构，因此优先任务应是**跟踪道路并识别赛道状态**；临时放置的障碍物才交给动态障碍检测模块处理。

## 2. 推荐的总体架构

```text
摄像头画面
  ├─ 赛道感知：道路区域、左右边界、车道虚线、箭头、特殊标记
  ├─ 动态障碍：与已知赛道背景不一致且位于行驶走廊内的物体
  └─ 状态判断：直道、左弯、右弯、窄口、路口、终点或异常
          ↓
     局部路径跟踪器
          ↓
     短时前进 / 左前 / 右前
          ↓
     重新获取画面并闭环修正
```

第一阶段不建议直接做“从整张图找一条任意路径”。先把赛道看成一条已知路线，完成可靠的道路跟踪；第二阶段再把分流、汇流和临时障碍抽象成节点图，加入 A* 或 Dijkstra。

## 3. 赛道应如何建模

### 3.1 已知赛道地图

建议人工把赛道制作成一张简化栅格图或中心线图，而不是要求手机摄像头一次识别整张地图。地图至少标记：

| 标记 | 含义 |
| --- | --- |
| `S` | 起点或发车区域 |
| `G` | 终点，图中黑白格线可作为候选标记 |
| `C` | 赛道中心线采样点 |
| `L/R` | 道路左右边界或安全边界 |
| `B` | 减速带、窄口等需要降速的区域 |
| `J` | 可能的分流、汇流或需要决策的节点 |
| `O` | 静态不可行驶区域，如中央绿化岛和装饰区域 |
| `D` | 运行时新增障碍物 |

对于当前图片，绿色岛、轮胎、停车位和水面等属于 `O` 或背景标记，不应等到运行时才把它们识别成未知障碍。真实小车运行时只需判断当前局部道路和新出现的 `D`。

### 3.2 摄像头视角下的局部状态

手机画面不是俯视图，赛道中的同一条直线在画面中会随着车身方向变化。因此每帧建议提取：

- 近处道路可行驶区域。
- 道路中心相对画面中心的偏移量。
- 中心线或左右边界的倾斜方向。
- 左前、正前、右前三个扇区是否有连续道路。
- 动态障碍物是否侵入车辆安全走廊。

控制目标不是让所有像素变成某个颜色，而是让车辆保持在当前道路走廊内，并沿道路切线方向前进。

## 4. 分阶段实现路线

### 阶段 A：静态赛道识别

暂时不让小车运动，收集赛道各段的手机画面：直道、左弯、右弯、窄口、减速带、起止线和装饰区域。

建议先用 OpenCV 完成：

1. 透视或区域裁剪，去除手机 App 的方向键、状态栏和固定按钮。
2. 根据深色道路与其他区域的颜色、亮度和纹理，提取道路候选区域。
3. 利用形态学处理连接道路区域，排除零散的植物、轮胎和文字图案。
4. 使用白色虚线和红白边界辅助估计道路方向。
5. 输出道路中心偏移、左弯/右弯建议和前方可通行比例。

这一阶段的输出应是带叠加标记的视频，而不是自动控制。必须先确认画面识别稳定，再接入触控。

### 阶段 B：低速道路跟踪

使用已确认的屏幕按钮映射：

- `up`：直行，前提是已确认实际行为。
- `up_left`：左前方行驶。
- `up_right`：右前方行驶。
- `down_left`、`down_right`：暂不用于首轮自动寻路，除非确实需要倒车脱困。
- 单独 `left`、`right`：只转车轮，不能当作前进或转弯行驶动作。

每次只发送很短的控制脉冲，等待新的手机画面，再计算下一次动作。控制周期应根据实测的 USB 截图耗时、手机到小车的视频延迟和小车惯性设置。

建议决策规则：

| 视觉状态 | 动作 |
| --- | --- |
| 道路中心基本对齐、前方直行 | `up` |
| 道路向左弯且左前走廊连续 | `up_left` |
| 道路向右弯且右前走廊连续 | `up_right` |
| 近处道路不清楚或左右都不确定 | 停止并等待人工处理 |
| 发现动态障碍侵入安全走廊 | 停止；首版不自动绕障 |
| 识别到黑白格终点线 | 停止并记录完成 |

### 阶段 C：赛道图与搜索

等道路跟踪稳定后，把赛道中心线采样成图：节点代表直道、弯道、窄口和特殊标记，边代表可行驶连接。运行时通过视觉识别标记或路段特征估计当前位置，再用 A* 搜索目标节点。

如果整张赛道只有一条确定路线，A* 的教学意义大于实际必要性；如果允许在路口选择、临时封路或新增障碍，图搜索和重新规划才会真正改变车辆行为。

## 5. 这张赛道的测试顺序

不要一开始在整张赛道上运行。按路段增加难度：

1. 下方停车区域附近的短直道：确认道路区域和前进按钮。
2. 单个左弯：确认 `up_left` 的转弯方向与释放行为。
3. 单个右弯：确认 `up_right` 的转弯方向与释放行为。
4. 连续 S 弯：测试闭环修正和摄像头延迟。
5. 窄路、减速带和中央岛附近：测试安全边界。
6. 黑白格线附近：识别终点并停车。
7. 最后才运行多弯道完整路线，并限制最大步数。

每段都记录：截图延迟、动作时长、道路中心偏移、是否人工接管、是否压线、是否碰撞和停止响应时间。

## 6. 对现有程序的调整建议

当前 `vision_navigation.py` 是“地面颜色分割 + 左中右通路”的局部避障原型，适合先验证障碍物概念，但不适合直接用于这张赛道。下一版应增加：

- 赛道道路颜色和虚线标记的独立检测。
- 车辆前方安全走廊，而不是只按画面左中右三等分。
- 道路中心偏移与弯道方向估计。
- 固定赛道装饰物的背景掩膜。
- 黑白起止线和黄色减速带等特殊标记识别。
- 视频画面延迟、动作完成和车辆停止状态记录。
- “未知就停车”的安全策略。

现有程序仍可作为实验一：在赛道上放置一个额外颜色明显的物体，验证近处障碍检测；道路跟踪应作为实验二单独实现，不能把两者混成一个没有明确验收标准的模型。

## 7. 当前不能从图片直接确定的事项

- 手机摄像头安装高度、朝向和视野范围。
- 小车实际行驶方向与手机画面上下方向的对应关系。
- 赛道是否存在真正的分岔、可选路线和规定行驶方向。
- 黑白格线是起点、终点还是仅作为装饰。
- 道路宽度与小车转弯半径是否匹配。
- App 的视频延迟、方向控制脉冲与实际位移的关系。
- 松开屏幕按钮后小车是否立即停止。

这些条件需要用实车和手机画面逐项标定，不能仅凭俯视照片推断。

## 8. 首轮验收标准

首轮不以“完整跑完整张赛道”为目标，建议达到以下条件后再扩大范围：

- 在三种光照下，能够区分道路、绿色岛和主要装饰区域。
- 直道连续运行时，道路中心不持续偏离。
- 单个左弯和右弯各完成至少 5 次，无碰撞且人工接管次数可记录。
- 画面丢失、方向不确定、App 弹窗或 USB 断开时进入停止状态。
- 检测到黑白格线后能停止，不依赖固定运行时间。
- 每次自动动作都有日志，能够回放“看到了什么、做了什么、为什么停下”。

达到这些条件后，才进入全赛道运行和 A* 路径规划。
